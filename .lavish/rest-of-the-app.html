And the structural finding — the reason you are unhappy with the rest

Two files carry everything non-engine

  • quiz/quiz-service.js — 884 lines: plan, pool, relevance registry, nine question builders, typed grading, the stream, drills, presets, the question count.

04 Settings — one object, two audiences

This is the piece that reshapes the plan. A single Settings object gates features for both audiences: developer levers we flip, and preferences the user flips in the Settings UI. One object, one read path — settings.compare reads the same whichever kind it is.

The one thing worth keeping visible inside that single object is which audience an entry belongs to. Declaring it on the entry, rather than leaving it to a naming convention, is what lets the Settings screen render exactly the user-facing rows without a second hand-maintained list — and it is the distinction that will matter the day a dev lever gets promoted to a user preference.

 *

The one rule this object must not break detailedStats gates screens, never storage. js/history/store.js must not be able to read it. The whole reason to keep full records for every user is that data you didn’t keep can’t be backfilled — a flag that reaches the writer would quietly destroy that.

Why question.js and grading.js are not per quiz type

Fair challenge, and the bare file list above was the reason it needed asking. The short answer: question.js holds the shape, not the generation — every line that builds a question is in builders/, one file per quiz type, exactly as you expected. And grading does vary, but not on the quiz-type axis. Three different things vary on three different axes here, and the layout follows the axis each one actually varies on:

ConcernVaries onLives in
Building a questionquiz type — four genuinely different jobs builders/, one per type
The shape a question hasnothing — one invariant across all four question.js
The identity it recordsnothing — one projection, or history rows differ by builder word-spec.js
Deciding if an answer is rightresponse mode — choice or input grading.js

Measured, so this is not a guess: of the ten question kinds in the registry, nine grade identically — an exact set match on value keys — and exactly one, produce, uses input mode. Keying grading on quiz type would mean four copies of the same set match. And the two axes are already known to come apart: the technical plan anticipates a “choose the correct spelling” question — a produce-style prompt with a choice response — and states the rule outright, “grading lives with the response, not the quiz type.” Type-keyed grading breaks on that question; mode-keyed grading does not.

There is a second reason, and it is your own rule 7. Grading is the boundary where “what the user did” becomes “a fact we store.” Right now that boundary does not exist — the choice branch is inside app.js and history.js re-derives expected a third time. One owner is the fix; four owners would leave the door open again.

The check that settles it This layout is not invented here — it is the Swift layout from technical plan §A.10, which already lists Question.swift, WordSpec.swift, Grading.swift and a Builders/ directory “one per quiz type”. The JS files are named for the same owners so the port stays a transcription. word-spec.js is back in the list above because rev 2 had collapsed it into question.js — your question caught that.

Also fixed here, because it is a symptom of the same confusion: the dead muʿtall drill. Per your note, QuizPlan stores engine types only — the group→type expansion happens once, at the boundary where a user choice becomes a plan, and the type→label direction is a display translation in glossary.js.

07 The object chain

Your progression, adopted whole: a plan describes what to draw from, a pool resolves what can be drawn, a run serves them, each is a question, each question produces an answer. The two things that were missing get names, and the two that were badly shaped get fixed.

QuizPlanWhat to draw from. Frozen configuration.→
QuizWordPoolWhat can be drawn. Resolved once, walked once.→
QuizRunThe live session over that pool.→
QuestionOne thing asked. Four named parts, not a flat bag.→
AnswerOne thing recorded. Is the history row.

Each object is built from the one to its left and knows nothing about the one to its right.

 * Every word the plan admits, resolved once. This is the object that was
 * missing: today three separate functions walk the same candidates for three
 * different answers — poolProfile() for what varies, conjugatable() for what
 * exists, randomWordSpec() for a draw — and none of them is a thing you can
 * hold, pass, or inspect.
 *
 * Relevance becomes a function of the POOL rather than of the plan, which is
 * more honest: a question dies because of what the pool contains, not because
 * of what was ticked.
 */
wordPool(plan) -> {
  candidates: [{ root, formId }],       // roots × forms that can produce words
  charts:     [{ tense, voice, mood }],
  cells:      number,                   // REAL cells — nils already excluded

  // what actually VARIES across the pool. This is the whole input to
  // relevance: a question is dead when its property is constant here.
  varies: { tenses, voices, moods, slots, forms, babs, derivedKinds, derivedForms },

  draw() -> WordSpec | null,           // one random word, or null if the pool is dry
}

relevance(pool, quizType) -> { live: Rule[], dead: Rule[] }

3 · QuizRun — the live session

/**
 * One live quiz. Owns everything that changes as you play. Screens read it and
 * call it; they hold no quiz state of their own.
 *
 * Today: seven fields on the UI's global `state` (quiz, stream, endless, index,
 * answers, selected, typed), advanced by four functions in app.js. The Swift
 * plan already names this type (§B.2), so naming it here makes that half of
 * the port a transcription rather than a design.
 */
class QuizRun {
  plan; pool; mode;        // preset id | 'custom' | 'endless'
  #source;                 // an array (fixed count) OR an iterator (endless)
  index = 0;
  answers = [];            // Answer[] — and these ARE the stored rows

  get current() -> Question
  get total() // null when endless — an absence, not Infinity
  get score() -> { right, total }

  answer(response) -> Answer   // grades, appends, returns. One path for both
                              // response modes, so no screen decides correctness.
  advance() -> boolean         // pulls from the stream when endless
  finish()  -> SessionRecord   // { plan, mode, startedAt, endedAt, answers }
}

4 · Question — four named parts instead of fifteen loose keys

/**
 * One thing asked. Today this is a flat object of ~15 keys in which identity,
 * display, response and explanation are indistinguishable, and readers pick out
 * the three or four they care about. The four parts below are the shape
 * TECHNICAL_PLAN §A.7 already specifies; the prototype drifted from it.
 */
Question {
  quizType, category,     // WHAT is being asked. Carried, never inferred from shape —
                          // inferring it is what silently misfiled new quiz types.

  identity: WordSpec,     // WHAT WORD it is about. Flat and serializable:
                          //   { rootKey, formId, verbType, tense, voice, mood,
                          //     slot, derivedKind }
                          // A KEY, never a Root reference — a stored answer must still
                          // say what it asked after the lexicon is edited.

  word,                   // the string on the card (or the citation, for the bāb question)

  prompt: {               // WHAT THE CARD RENDERS. Tagged, so the screen switches on
    kind,                 // 'word' | 'spec' | 'meaning' | 'derived' — one renderer each
    text, gloss,          // …and cannot accidentally render the answer, which is the
    chips, radicals,      // live hazard on the meaning card today
  },

  response:               // HOW YOU ANSWER, and what counts as correct
    | { mode: 'choice', options: [{ ar, en, valueKey }], correct: Set<valueKey> }
    | { mode: 'input',  accepted: [string] },
                          // note: `correct` is a set of VALUE KEYS, not indices — so
                          // shuffling options can never change what is correct

  feedback: { meaning, explanation },   // shown after; tips are computed, not stored
}

/**

10 Risks worth naming now

A1 has no visible payoff

The one step that ends with the app looking identical — which is what makes it easy to let drift into a redesign. Its defence is parity: the 294 assertions must stay byte-identical, and every screen gets walked before and after.

A flag is only as good as its single owner

The two failure modes are already visible: detailedStats reaching the history writer, and the content flags becoming a second answer to “is this type playable” beside availableTypes(). Both are cheap to prevent now and expensive to unpick later.

The freeze locks the engine API

After B3, changes are a reviewed corpus diff. Anything the Swift app will ever need from ConjugationService must exist before that point — including whatever a dev-only Compare needs, if Q2 goes that way.

The spec documents now disagree with the plan

PRODUCT_SPEC §3 promises a free/Pro matrix and §6 promises all seven verb types at launch. Neither is true under the Settings decision. They need editing when A1 lands, or the next reader builds from a stale contract.

Tips need writing, not just wiring

The registry is an afternoon; the tips themselves are content, and a thin one reads worse than nothing. Worth deciding a target — one good tip per question category is the honest minimum for A3 to count as done.

The muʿtall drill was silent for weeks

It failed safe — greyed out, no error — which is why a headline feature being dead went unnoticed. Worth a cheap guard: a startup assertion that every shipped preset produces at least one question.
