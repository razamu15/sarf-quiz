06 chart-spec.js — do we still need it?

Yes, and it is one of the three most-depended-on files in the codebase 12 files import it, including all five conjugators. What was deleted in A1 was the chart string — chartKey() and chartShape(). What remains is the ChartSpec type, which is a different thing and is load-bearing.

The confusion is fair, because the file's job narrowed. It used to do two things: name a paradigm as an object, and crush that object into a string so other layers could key data by it. Only the second one was the problem. Here is every export, measured:

ExportImportersWhat it does, and why it stays
chartSpec()6 The constructor, and it normalises. It forces mood to null outside the muḍāriʿ and voice to maʿlūm for the amr — a caller passing a manṣūb māḍī is corrected rather than obeyed. That is what stops two specs for the same paradigm comparing unequal, and it is the reason this is a function and not an object literal. core

The short answer Keep the file, delete two exports. Five of seven are load-bearing and one of them is called by every conjugator. The name is still accurate — after A1 it holds exactly what it says: the chart as a spec. Say the word and I will remove usageOf and the re-export line; both are provably unreferenced, so it is a two-line change with no risk.

One smaller thing the audit turned up

The bāb is looked up in two places babOf(spec) in this file and wordSpec() in quiz/word-spec.js both compute root.forms[formId]?.bab. Same fact, two derivations — exactly the class of duplication A1 spent its time removing, and I introduced it. The fix is to make babOf take (root, formId) instead of a spec so both call it. Small, and worth doing before it becomes three places.

If those two ever disagree, the service wins; the filter is an optimisation, not an invariant.

09 chart-spec.js — dissolved

You were right, and I was defending a rationale I had not checked I argued chartSpec() earned its place because it kept specs comparable and because specs were stored as identity. I then went and checked both claims. Neither holds:

Nothing in the codebase ever compares two specs. No ===, no deep equal, nothing.
No ChartSpec ever reaches a Question or a history record. Questions carry a WordSpec, built from a spec's fields — the spec itself is discarded. So the Object.freeze was guarding an object nobody stores.

Which leaves exactly what you said it was: two silent defaults and a rewrite, behind a name that does not say so.

And the rewrite was worse than a smell — it was a second, contradicting validator

isValidShape() already existed and already judged this, at the boundary chartExists() where your rule 7 says a check belongs. chartSpec() was a second judge that corrected instead of rejecting, and the two disagreed: 

// the real guard, in conjugation-service's precondition:
isValidShape({ tense: 'madi', mood: 'raf' })   →  false   "invalid — return null"

// the constructor, on the same input:
chartSpec({ tense: 'madi', mood: 'raf' })      →  { mood: null }   "valid — here you go"

And the Tables browser hit this on every single māḍī view. The screen keeps a mood in UI state so the chips remember your selection when you flip tenses — so it was handing over {tense:'madi', mood:'raf'}, a shape the guard rejects, and the constructor laundered it into a valid one before the guard ever saw it. Nothing failed, so nothing surfaced it. That is the real cost of a correcting constructor: it does not fix a bug, it hides one.
