What the iOS codebase looks like — targets, features, views, and who owns which piece of state

The prototype is 48 files of imperative DOM. SwiftUI is declarative and component-based, so the whole top half of that structure stops applying — but only the top half. This is the shape of the replacement, at outline altitude: three targets, four tabs, seven features, one view model. Every claim about the prototype below was read out of the source, not remembered.

What this is not: not the port schedule (ROADMAP.md Track C), not the file-by-file inventory (PORT_INVENTORY.md Part 4), not the engine's design (TECHNICAL_PLAN.md Part A). Those already exist and are not repeated here. What is genuinely new is §04–§07: the component hierarchy and the state map, which no doc covers today. §10 is the handful of decisions this shape still needs from you.

01 Three rings — the boundary decides the structure, not the other way round

This split is already decided in PORT_INVENTORY §3.2; it is restated here because everything below hangs off it. The rule that produced it is one sentence: a target is a group of code that changes for the same reason. The morphology is heading for a freeze; the quiz rules churn every roadmap step; the views are being written for the first time.

Arrows point at what a layer is allowed to know about. The dotted edge at the bottom is the one that must stay impossible.

SarfCore

Root letters in, a fully-vowelled word or nil out. It never returns a domain object — only strings — which is why the API surface is tiny and the boundary is cheap.

Contains no display strings and no product copy. Freezes at the corpus export.

SarfQuiz

Turns a pool of words into questions worth asking, and judges the answers. Glossary lives here, not in Core: an AnswerOption.en literally is TENSE_LABELS[t].en, and the two must not drift.

No SwiftUI import — a compile error, not a convention.

SarfQuiz.app

Views, navigation, storage, StoreKit later. Holds no rule about Arabic and no rule about correctness. The screens ask; they never decide.

This is the only target with @MainActor everywhere.

What the boundary buys, concretely Swift defaults to internal, so "ConjugationService is the only door" stops being a rule you keep by reading imports and becomes a fact the compiler enforces. The app cannot call SalimConjugator or read a stem table even by accident.

01

Views never compute a domain fact. No screen decides whether an answer is right, whether a chart exists, or which questions are worth asking. It asks a package.

02

One view model in the app: QuizRun. Everything else is value state plus views over it. A feature gets an observable object only when it owns something that outlives a view and mutates.

03

Features never import each other. The moment two features need the same view, it moves to Components/. Cross-feature navigation goes through AppState.

04

Nothing in Features/ touches SwiftData or UserDefaults. Services/ owns storage, exactly as history/store.js does today — and for the same reason: no flag may reach the writer.

05

State lives at the lowest level that outlives the view that reads it. That single rule produces the whole of §06 — and it is what keeps the wizard's step out of plan data.

06

Files stay under ~400 lines, screens under ~200. A screen file is a layout; its child views sit beside it in the feature folder rather than nested inside it.

Why Results lives inside the cover

A finished quiz is still the quiz. Putting ResultsScreen inside the same cover means "Back to home" is one dismissal, "New round, same setup" swaps the run without any navigation at all, and the tab bar stays suppressed the whole time — which is exactly what main.js achieves today by not appending it.

The two cross-feature jumps

There are only two, and both are one assignment on AppState: quiz feedback → a chart (tables = …; tab = .tables; run = nil) and Home's stat card → Stats (tab = .more; path = [.stats]). Neither feature imports the other — they write shared state and let the router react.

05 The quiz screen — the one component that is a rewrite, not a port

screens/quiz.js's submit() reaches into already-rendered buttons and mutates them: remove the Check button, strip .selected, add .correct or .wrong, append the feedback box. None of that has a SwiftUI translation. The fix is not a trick — it is a modelling change: the after-state stops being applied and becomes derived. 

// Components/AnswerOptions.swift
enum OptionState { case idle, selected, correct, wrong, dimmed }

func state(for option: AnswerOption) -> OptionState {
    guard let answer else {
        return run.selected.contains(option.valueKey) ? .selected : .idle
    }
    if question.response.correctKeys.contains(option.valueKey) { return .correct }
    if answer.given.contains(option.valueKey) { return .wrong }
    return .dimmed
}

The screen needs one piece of state it does not have today — the answer for the current question — and QuizRun already stores every Answer and knows isAnswered, so it is a bounds-checked read at run.index. No model change. Everything else on that screen falls out of the same move:

// App/AppState.swift — the app-session tier, and nothing else
@Observable @MainActor
final class AppState {
    var tab: AppTab = .home
    var draft = PlanDraft()          // struct — the Practice chips bind into it
    var tables = TablesSelection()   // rootKey · formId · tense · voice · mood · highlight
    var search = ""
    var run: QuizRun?                // non-nil ⇒ the quiz cover is up
    var replay: (() -> QuizRun?)?    // "new round, same setup"
}

The invariant that must survive the port

Neither Practice flow builds a QuizPlan. Both take a @Binding<PlanDraft> and only paint chips; PracticeScreen makes the single draft.plan() call on the start path. That is what lets the losing flow be deleted with no migration — and in Swift it gets stronger, because PlanDraft is a value type: a flow that tried to build a plan would have to be handed the type that makes one.

One place the port needs new machinery

The wizard opens at step 1 every time (decided, A2·Q5). Today that is free — resetPracticeFlow() on tab entry. SwiftUI keeps a tab's view tree alive across tab switches, so @State would silently remember the step. It needs an explicit reset on appear. Small, but it is the kind of behaviour that disappears quietly in a port.

The one performance-shaped structure decision wordPool() walks every candidate × chart × ṣīghah calling conjugate(), and Practice re-runs it on every chip tap to show the count under Start. On a phone that will jank. Because SarfCore is nonisolated and Sendable, the walk can run off the main actor — so Practice owns a small PoolPreview holding {pool, live/retired kinds, count, sample}, recomputed by .task(id: draft). That is the only computed cache in the app, and it is the reason Practice is the one feature with more than views in its folder.

Three names this outline changes, and why

SarfCore.ArabicText → and, separately, DesignSystem.ArabicWord
The package keeps ArabicText (grapheme clustering — used by grading and the chart diff). The view that displays Arabic must not share that name; a reader seeing ArabicText(word) in a body cannot tell whether it renders or computes.
Services/Settings.swift → AppSettings
Settings is a SwiftUI scene type. A settings store that collides with a framework noun costs a disambiguating import at every use site.
Prompt · Response → Question.Prompt · Question.Response
Nested rather than top-level. Response alone is a network noun, and ExplainService arrives later in the same app. Nesting states the ownership the prototype's file comment already claims: these are parts of a Question, not free types.
The trap that outranks every structural choice here JS indexes strings by UTF-16 code unit; Swift indexes by grapheme cluster. Four engine sites transcribe "correctly" and silently produce wrong Arabic — مُتْتُ for مُتُّ, كْتُبْ for اُكْتُبْ. That is PORT_INVENTORY §1.1, it is not a structure question, and no amount of good architecture prevents it. Named here only so this document is not mistaken for the whole plan.

10 Decisions this outline still needs

Five. The first three change view code everywhere and are cheap now, expensive later; the last two are structure choices I have a recommendation on but did not want to take silently. Pick in place — each queues one prompt back to me.

1 · Deployment target

Affects every view file. @Observable needs 17; newer TabView and Layout conveniences need 18+.

Queued — press Send to Agent when you are done.

2 · iPad in v1?

Not a stretch of the phone column — a different navigation structure (NavigationSplitView), decided before views are written or retrofitted after.

Queued — press Send to Agent when you are done.

3 · Does an interrupted quiz resume?

History is safe either way — answers persist as they happen. This is only about the in-flight run, and it decides whether QuizRun must be Codable.

Queued — press Send to Agent when you are done.

4 · One QuestionCard, or two?

The prototype keeps two exhaustive prompt tables on purpose (§07). Swift's enum switch replaces the reason for that.

Queued — press Send to Agent when you are done.

5 · One view model, or one per feature?

The whole app's state fits in §06's four tiers with exactly one observable object (QuizRun) plus one async cache in Practice. The alternative is the conventional MVVM shape: a HomeModel, TablesModel, ResultsModel beside every screen.

Queued — press Send to Agent when you are done.

Once these five land, the next artifact worth making is the level below this one: the Practice feature drawn in full — both flows, the controls, the pool cache and the summary — because it is the screen with the most state and the one that proves the pattern for the other six.
