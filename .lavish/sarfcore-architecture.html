The mental model

Words are generated, never stored

A conjugated word is four pieces snapped together. Two pieces are grammar (same for every verb), one is lexicon (the root's letters), and one is a choice (which cell of the table you want). That's the whole engine — everything else is bookkeeping around this equation.

Two elegant consequences: the wazn of any word is the same pipeline run on the reference root ف ع ل, and every generated word is born knowing its root, form, bāb, tense, voice, mood, and slot — no lookup needed, which is exactly what quiz explanations and (later) AI Explain consume. Irregular verbs (قال، رمى) skip the equation entirely: they're hand-typed lookup tables checked before the engine runs.

Static structure

Who depends on whom

Three layers. Data flows top to bottom exactly once at app launch; after that every arrow is a plain synchronous function call. Nothing in SarfCore has mutable state — the only stateful objects live in the app layer.

Execution path 1

App launch — JSON becomes live objects, once

This is the only place JSON exists at runtime. After AppModel.init returns, the files are never touched again — every later call works on decoded Swift values held in memory.

Execution path 2

Tapping “Start” on a drill — the hot path

The generator is probabilistic: it rolls random (root, form, tense, voice, slot) combos and asks the Conjugator “does this word exist?” — nil means reroll. Bounded retry loops (80 for a word, 400 for a drill) guarantee termination even on sparse content.

Execution path 3

Inside conjugate() — the heart of the engine

Every Arabic word in the app is born here. Note the order: override tables win before the engine even looks at the grammar — that single check is the entire irregular-verb mechanism.

The content pipeline

Why the JSON exists at all

The JSON is not a database — it's a hand-off format between two implementations of the same engine. The web prototype is where content is authored and instantly play-tested; the export script freezes its JS constants into JSON; the Swift package decodes them. The 125-assertion smoke test runs on both sides to prove the two engines agree.

patterns.json ← patterns.js

The grammar. Slot lists, pronoun labels, māḍī/muḍāriʿ(×3 moods)/amr affix tables, prefix letters, the 6 abwāb, all 10 form specs (Form I stems materialized per bāb so the JSON stays logic-free), mood/meaning/verb-type labels. Closed data — adding verbs never touches this file. Decodes into GrammarTables.

roots.json ← roots.js

The lexicon. 24 roots × their forms: bāb, gloss, transitivity, samāʿī maṣdar, English conjugation bits — and for قول/رمي, complete hand-typed override tables (7 tables each). Growing data — all future content work lands here. Decodes into [Root].

Both files are NFC-normalized at export so Swift string equality is exact, and marked GENERATED — do not edit. The workflow after any content change: node test/smoke.mjs → npm run export-content → ./build-and-test.sh.

Your review questions, answered (plan updated in place)

Q1 · What do the new objects actually look like?

Real literals below — a full chart from SalimGrammar.swift (all 14 rows visible, checkable against the paper chart), a decoded root, and the routing + history types. Now also in plan §A.3–A.5, A.7, B.3.

Q2 · Is bundled roots.json viable for the real app?

Yes — it's the standard iOS pattern for read-only content, not a prototype shortcut. The file ships inside the app bundle: offline by construction, versioned with the binary, decoded once at launch (hundreds of roots = single-digit milliseconds), validated at load and in CI. The growth path when scale or freshness demands it: bundled JSON → precompiled store/SQLite (thousands of entries) → server-delivered content packs (update verbs without app releases). Only LexiconService ever knows which one is in use. Bonus added to the plan: since verb-type classification is mechanical (weak letters/hamza/doubling are visible in the radicals), the loader cross-checks each root's declared type against its radicals and rejects mislabeled content loudly.

Q3 · How does ConjugationService pick the right engine?

Dictionary lookup — no loops, no probing, no type fields on grammar objects. Every Root already carries its VerbType (it's in roots.json today: type: "salim"). The service is built with a list of engines, each declaring handles: VerbType, keyed into [VerbType: any VerbTypeConjugator] at init. A call does engines[root.type] → O(1); if no engine exists yet for that type, it falls back to the root's hand-authored fixture table; else nil. The grammar objects don't need labels because they never float free — SalimConjugator owns SalimGrammar, full stop.

Q4 · Will the data model support history & mistake analysis later?

Designed for it now: every question is born with a QuestionIdentity (category, form, verb type, chart, root, slot) because the engine generated it — nothing to re-derive. Options carry a valueKey (the enum value they represent), so an answer is recorded as what was picked, never which button position (positions are meaningless after shuffling). The stored AnswerRecord = identity flattened to typed fields + pickedValues/correctValues sets (multi-select-aware). That's what makes “common mistakes” real analysis later: picked 2ms when the answer included 3fs aggregates into “you confuse أَنْتَ forms with هِيَ forms” — a weak-spot drill seed, not just a wrong-count. Full schema in plan §B.3.

Friction points — your triage

What's confusing today, and what improving it would mean

Your triage is recorded: #1 GrammarTables — DISCUSS (proposal: Glossary split, see Part 2) · #2 FormEntry naming — DISCUSS (proposal: RootFormUsage) · #3 grammar-as-JSON — IMPROVE · #4 stringly keys — IMPROVE (ChartID) · #5 two engines — DISCUSS (retirement path in §A.9) · #6 file naming — IMPROVE (services convention) · #7 Conjugator oddities — KEEP. The original cards stay below for reference; re-queue if you change your mind.

1 · GrammarTables is a grab-bag NAMINGSTRUCTURE

One type holds two unrelated things: the engine tables (affixes, stem templates — what Conjugator needs) and display strings (pronoun English, meaning labels, verb-type labels — what only the UI needs). The name says “tables” but you also go there for meaningLabel().

Improvement: split into Grammar (engine data) and a Glossary/Labels catalog (display strings), so each consumer imports only what it uses.

2 · FormEntry vs FormSpec NAMING

Two types with near-identical names mean opposite things: FormSpec = the grammar of a form (stem templates, same for every verb); FormEntry = one root's usage of a form (its gloss, bāb, transitivity). This is probably the single biggest source of “which one do I want?”.

Improvement: rename FormEntry → something lexicon-flavored, e.g. Lexeme, VerbSense, or RootForm — or fold the distinction into the doc comments + a naming convention (grammar side keeps “Spec”).

3 · Closed grammar shipped as JSON STRUCTUREPIPELINE

The affix tables and form specs are closed linguistic facts — they change only if the model of the grammar changes. Shipping them as JSON buys nothing (they're not content anyone edits) and costs a lot: decode ceremony, string keys, validateCompleteness(), fatalError accessors, and the stems/stemsByBab either-or dance.

Improvement: write the grammar as Swift literals (compile-time checked, no validation path at all) and keep JSON only for roots.json — the actually-growing content. The export script shrinks to roots-only; the smoke test still proves JS/Swift agreement.

4 · Stringly-typed keys under the hood STRUCTURE

Enums exist at the edges, but internally it's strings: override tables keyed "mudari_malum_jazm", Form I stems keyed "1"…"6", Root.forms keyed "I"…"X", meanings as [String]. A typo in content silently becomes “that combination doesn't exist”.

Improvement: decode into enum-keyed dictionaries at the ContentStore boundary (custom Decodable), so a bad key fails loudly at load instead of vanishing. Pairs naturally with #3.

5 · Two engines to keep in sync PIPELINE

Every engine behavior lives twice: conjugator.js and Conjugator.swift (ported line-for-line, verified by twin 125-assertion suites). While the web prototype is your design playground this is a feature; once the iOS app is the real product it becomes a tax on every engine change.

Improvement (later?): declare Swift the single engine after Phase 2 sign-off; keep the web prototype as a content-authoring/preview tool only, or retire it. Not urgent — worth deciding when, not if.

6 · Names that describe files, not roles NAMING

MorphologyPrimitives.swift is “the enums”. patterns.json holds far more than patterns (pronouns, labels, verb types). GrammarTables we covered. ContentStore is fine but “store” hints at persistence it doesn't have (it's a loader).

Improvement: one consistent metaphor across the package — e.g. Vocabulary (enums) / Grammar (rules) / Lexicon (roots) / ContentLoader. Cheap to do, big legibility win, mostly mechanical rename.

7 · Small oddities inside Conjugator STRUCTURE

The SyntheticRoot trick (wazn = conjugate ف-ع-ل) is clever but surprising on first read; citation() carries a special display-only path for Form IX; overrideTableKey re-derives the same string keys the JS side invented. None are bugs — they're places a first-time reader stumbles.

Improvement: mostly documentation + small extractions (e.g. a named WaznRenderer facade, an enum for table keys). Low priority unless we're already touching those files for #3/#4.
