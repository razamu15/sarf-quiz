02 What the queries found

F1

Q23 cannot be answered by any record that stores fields instead of the question

“Show me Tuesday’s session as I saw it” needs the prompt text, the four options, the contextual meaning and the explanation. A field-copying record throws all of that away — and Q21 proves it is unrecoverable in principle, not merely inconvenient: the distractors were sampled and shuffled at build time from a random draw. Re-running the builder gives different options.

This is the query that decides your Answer question, and it decides it your way. It also quietly explains a smaller oddity: the results screen shows a vocab recap, but fullMeaning is never written to storage — the recap works only because it reads the live question object. A stored session could not reproduce its own results screen.

ResolutionEmbed the Question whole. Detail and cost in §03.
F2

The chart is stored as one composed string, and three queries want its axes

chart: 'mudari_malum_raf' answers “accuracy on this exact chart” and nothing else. Q10 wants “majhūl across every tense”, which means reversing the key on every row through chartShape() before you can group. It works, and it is the wrong shape — the axes are first-class everywhere else in the system, and chart-spec.js already says the key exists only because stored records needed a string.

You asked whether chartKey can go entirely. It can — from production, completely. There are exactly three call sites and none of them survives its own replacement:

Call siteWhat it doesAfter
quiz-service.js:333 chartId: chartKey(spec) — composes the stored chart identity the three axis fields on identity, per this finding
app.js:857 chartShape(q.chartId) — immediately decomposes it again for the “See the full table” deep link reads the same three fields. A pure round-trip that simply disappears
conjugation-service.js

That third one is worth stating precisely, because it is stronger than “can be removed”. I instrumented a full sweep: of 14,638 conjugated words, 14,638 come from an engine and 0 come from a fixture. Both roots carrying manualTables — قول and رمي — now have working engines (ajwaf, nāqiṣ) that take precedence in the router. The fallback path is dead code today, not at the freeze. B3 was already scheduled to delete it; nothing is waiting on that.

chartShape() exists only to reverse chartKey(), so it goes with it. CHART_SHAPES and isValidShape() stay — those are the axes as data, which is the thing we are keeping.

ResolutionRemove chartKey() and chartShape() from production. Store the three axes as fields.
F3

QuizPlan cannot express the drill a weak spot asks for

Q18 finds “you are weak on doer × Form II”. Q19 turns that into a quiz. But a plan carries quizType, tenses, voices, moods, forms, types, count — it can narrow the pool, not the question. Which questions get asked is decided by relevance() from what the pool contains. So the best a weak-spot drill can currently do is restrict forms to ['II'] and then take tense, voice, doer, iʿrāb and bāb questions at random — most of which are not the weakness.

This is a genuine architectural finding, and exactly the kind your sequencing was meant to catch: it is invisible until you write down what the drill button has to do. It also has a second use — a “drill just the doer question” option in Practice is the same field.

DecidedPool-only, and the drill is knowingly approximate. No questionKinds field on the plan. Recorded below so it stays a tracked choice rather than an oversight.
Tracked decision — carry this into the code as a named comment A weak-spot drill narrows the pool, not the question. Told “you are weak on doer × Form II” it restricts forms to ['II'] and then serves whatever kinds relevance() offers — so the drill is diluted by the questions you were not weak on. This is chosen, not overlooked. The comment lands in quiz-plan.js’s header and at the planFromWeakSpot() call site, so the next reader finds the decision rather than re-deriving it as a bug. Revisiting it means adding an optional questionKinds to the plan, which intersects with the live kinds and can narrow but never resurrect a retired one.
F4

The bāb is in the spec’s dashboard and not on the record

Spec §5.4 lists bāb among the breakdown dimensions, and the bāb question already exists in the quiz. But a bāb answer stores formId: 'I', chart: null, slot: null and no bab. You would recover it by looking rootKey up in the lexicon — from mutable data. Correct one root’s bāb and every historical record about it silently changes meaning; remove a root and the lookup fails.

ResolutionPut bab on the identity. It is a fact about the word that was asked, so it belongs with the word that was asked.
F5

Q24 trusts a stored plan instead of validating it

Sessions store the plan verbatim so a setup can be replayed — good. But a plan written by an older release can name a verb type that has since been split, a quiz type that was renamed, or a form whose content has gone. Handing it straight back to the quiz builder is trusting storage.

ResolutionplanFrom(stored) validates on the way in and drops what no longer exists — reporting the drop rather than silently narrowing the quiz.
F6

Two dead exports, found while auditing chartKey

CHART_LABELS in glossary.js — nine chart-keyed label entries (المُضَارِع المَرْفُوع and friends) — is referenced nowhere. The Tables browser builds its title in app.js by composing TENSE_LABELS, VOICE_LABELS and MOOD_LABELS, which is the axis-shaped way and the one to keep. CHART_LABELS is the last display-side survivor of the chart-as-string era.

Same for the isConjugatable() gate in conjugation-service.js, whose entire job is to ask “does this root have manualTables if it has no engine?” — a question that now has one answer for every root in the lexicon.

ResolutionBoth deleted with the fixture path. Flagging rather than removing silently — they are outside A1 (a)’s scope.
And what is already right Eighteen of twenty-four need nothing new. Two decisions already made in this codebase are why: values are stored semantically (pronoun keys, not button positions), which is the whole of Q20; and quizType is carried on the question rather than inferred from its shape, which is the whole of Q14 and Q15 — the note in history.js says it used to be guessed downstream and “silently misfiled any new quiz type that happened to be multiple choice”.

03 The Answer shape — your question, settled

“i think the answer entity should embed the question entity that was asked for it. why are we not doing that instead of copying a bunch of fields directly which makes it so we have to reconstruct what was asked instead of just copying it?”

You are right, and the query list makes it concrete. Two things were wrong with the copy list. First, the reason I gave for copying does not hold: I said a stored record must survive the lexicon changing — but Question.identity is already a flat, key-based projection built for exactly that (rootKey, never a Root reference), so embedding it reintroduces nothing. Second, and worse, copying loses data that cannot be recovered: F1 and Q21 above.

So the domain object embeds. What the query list adds is the one real constraint on how it is stored, and it is a platform fact rather than a design preference:

What Q23 wants

The whole question, verbatim — prompt, options, meaning, explanation — so a session can be redisplayed exactly as it was answered.

Free in JS. The record is JSON either way.

What Q7–Q18 want

Flat fields to group and filter by: category, formId, verbType, quizType, slot, bab, the three chart axes, correct, answeredAt.

Not free in Swift. SwiftData predicates and grouped fetches work over stored properties; fields buried inside an embedded value are not indexable the same way.

The resolution — the domain object embeds, the storage layer projects

// ---- the domain object: what the run holds, and what you read ----
Answer {
  question:  Question,      // embedded WHOLE. Nothing copied, nothing reconstructed.
  given:     [string],
  expected:  [string],
  correct:   boolean,
  divergeAt: number | null,
  answeredAt,
}

// ---- the storage layer: the ONLY place that knows about query columns ----
// js/history/store.js in JS, HistoryService in Swift. It writes the embedded
// answer AND a flat index derived from question.identity. Every field in the
// index is a copy — deliberately, and in one place, because it is an INDEX and
// not a second source of truth: the embedded question stays authoritative and
// the index is rebuildable from it at any time.
function rowFor(answer) {
  const { identity, quizType, category } = answer.question;
  return {
    ...identity,            // rootKey, formId, verbType, bab, tense, voice, mood, slot, derivedKind
    quizType, category,
    correct: answer.correct,
    answeredAt: answer.answeredAt,
    answer,                 // ← the whole thing, for Q21 and Q23
  };
}

This is the same move LexiconService already makes: one type knows where the data lives, and everything above it is unchanged. In the prototype rowFor() is nearly a no-op — localStorage takes the object as-is. In Swift the same function is what fills the @Model’s stored properties. Your rule 7 holds: the projection happens once, at a boundary, and no reader does it.

The alternative, and why I am not recommending it Store only the embedded question and derive the index at read time. It removes the duplication entirely and is genuinely tempting. The cost is that every dashboard query decodes every record — fine at 2,000 answers, not fine at 50,000 on a phone, and the whole premise of keeping full history for every free user is that the number gets large. It also gives up store-level filtering, so “Form VII only” becomes a full scan. If you would rather take that trade to keep one source of truth, say so — it is a defensible call and it is reversible later, which the reverse is not.

05 Decisions

D1 · settled — embed the Question, plus a flat query index owned by the storage layer The domain object embeds the whole Question; history/store.js alone derives the flat columns the dashboard groups by. The index is a copy in one function, rebuildable from the embedded question at any time — an index, not a second source of truth. Queries stay cheap at any size and SwiftData can filter in the store.
D2 · settled — weak-spot drills narrow the pool only No questionKinds field on QuizPlan. The drill is knowingly approximate, and that choice is recorded as a named comment in quiz-plan.js and at the planFromWeakSpot() call site, so it reads as a decision rather than a bug. Full wording in F3 above.
D3 · settled — the catalogue is complete Twenty-four queries, closed. A1 (b) designs the object chain against them.
D4 · settled — existing stored history is disregarded No migration and no key bump. Records under sarf.history.v1 carrying chart: 'mudari_malum_raf' strings simply stop being read; the new shape writes over them. Your call, and the right one — it is your own test data, and A1 (b) changes the record wholesale anyway, so a migration would be throwaway work for a shape that is about to change again. Worth noting this cost is prototype-only: it lands long before any user has history worth keeping, which is itself an argument for making the record change now rather than after the port.
