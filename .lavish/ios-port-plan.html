The one thing to resolve before any slice can be ordered

TECHNICAL_PLAN.md Part C argues, at length, that the whole engine ports as one atomic, gated unit before any Swift UI exists — because chart-correctness bugs are found by reading whole tables, and that loop is fastest in the browser. You just asked for the opposite: pair UI with logic per slice, so each step is something to look at. These aren't actually in conflict — but which one wins where matters, so it's a real decision rather than a default.

Decision 1

How does "engine-first" coexist with "tangible per slice"?

Four more calls, each small on its own

Decision 2

Two Swift packages or three?

✓ confirmed: 3 targets

Your three questions, answered directly:

"What benefit does a separate SarfQuiz actually give us?"

Four, in order of how much they'd bite you: (1) "no UI in the quiz rules" stops being a convention you keep by grep and becomes a compile error — importing SwiftUI into SarfQuiz won't build. (2) SarfCore heads for a hard freeze at B3; the quiz layer is explicitly the least settled part of the app (Practice keeps reshaping, tips keep growing, Compare adds a diff) — one package means the frozen thing's version moves every time the unfrozen one does. (3) grade() and relevance() get real headless tests with zero simulator/SwiftUI dependency, provably. (4) the boundary doubles as the concurrency boundary (§3.3f) — SarfCore stays nonisolated/Sendable so wordPool()'s per-chip-tap recount can run via Task.detached without janking the main thread.

"How hard is it to move to the app target later?"

Cheap in that direction — deleting a target and folding files into the app is boilerplate, no logic changes, nothing breaks by loosening a boundary. The asymmetry is the reason to start with 3: going the other way — splitting quiz rules back out of an app target they've been living in for months — means first auditing every place a View reached past the intended surface, because nothing stopped it from happening. Cheap to remove a wall later; expensive to build one after things have grown through the gap.

"What if the view layer needs more access to quiz building / question rules than expected?"

That's a public surface question, not a package question — exactly like ConjugationService already works today: FORM_META stays internal, but conjugates()/hasPassive() are exposed as behaviour. If a screen genuinely needs more of SarfQuiz, you widen what's public — you don't need to move the file. The one thing that would need a real change is a screen constructing its own plan directly — but that's already forbidden by D-34 regardless of how many targets exist, so it isn't a new risk this boundary introduces.

One honest note: this isn't hypothetical future friction — 2 of the boundary's benefits are already true today, on the JS as it stands (the FORM_META leak, the glossary.js reach), which is some of why the recommendation didn't change.

Same principle as D-07 (prototype-first): don't port a screen that's about to be rebuilt. The bar for "needs a JS pass" is that there's real design left to work out cheaply — not just "the prototype hasn't built it yet."

The layer you flagged

Mitigating relevance.js / word-pool.js / quiz-plan.js

This is where the domain rules live with the least test-by-inspection: relevance.js is 135 lines deciding which questions are even worth asking, word-pool.js walks every candidate × chart × ṣīghah once and has to run off the main actor, and both feed a builder layer that samples and shuffles randomly — so you can't just diff the output the way the engine's golden corpus does. Six things, in order of leverage:

biggest lever

1 · Shrink it in JS before Swift sees it

The parse card (Decision 3) collapses 5 question-builders into 1 and deletes the drill-bundle logic — about −200 lines off this exact layer, per PARSE_CARD_PLAN.md's own count. Swift ports the settled, smaller shape once, not the churning one now and a rewrite later.

structural

2 · Its own package, no UI imports

Decision 2's SarfQuiz target: nonisolated, Sendable, headless XCTest, no SwiftUI import possible. "Reviewed the rules in isolation" becomes provable, not just intended.

new

3 · A pool-parity fixture

Extend the golden-corpus discipline one layer up. For the 6 canonical plans already measured in product-spec/screens/03-practice.md (1,400 / 2,548 / 700 / 2,100 / 300 / 5,396 cells), dump JS's {cells, varies.*, live/dead axes} and assert Swift produces the identical numbers. Deterministic, so it diffs like the engine does — the randomized part (individual draws) is what property tests are for, below.

4 · Property tests for the builders

Can't diff a random draw byte-for-byte, so assert invariants instead: doer's correct set is exactly the slots rendering identical text; every axis's correct set is non-empty; a card missing a live axis never ships. Same technique TECHNICAL_PLAN §B.6 already plans for the engine.

5 · Port literally, refactor separately

The first PR for this layer is a 1:1 transliteration — same function names, same shape, easy to eyeball against the JS source line by line. Any Swift-idiom cleanup (the space → Set to distinctAnswers → Int rework, already scheduled for JS in Decision-adjacent prep work) is its own, separately reviewed PR.

6 · One synchronous walkthrough

Not async PR comments for this one. A single sit-down pass through relevance.js + word-pool.js + quiz-run.js side-by-side with their Swift port, before merge — scheduled explicitly as Slice Q2's exit criterion, not left to whoever happens to open the PR.

The roadmap

Five tracks. Track D (new) ports the design system's tokens and components into SwiftUI in parallel with Track P — neither depends on the other — so that E1's Tables screen is the real, fully-designed buildout from day one, not a placeholder redone later. Solid arrows are hard blockers.

The وجل regression is scoped to E2 alone (it's a mithāl content bug) — it does not touch Q2's pool-parity fixture, which is measured against sālim-only setups.

Every slice, with its exit criteria

D D1 / D2 — the design system ports to SwiftUI new, parallel to Track P, ahead of E1

D1 — colours as an asset catalog (Paper/Night pairs for every semantic token: ground, ink, sign, correct/wrong, etc.), Scheherazade New + Newsreader bundled as fonts, the type scale (arabic-hero through caption) as Font extensions with the explicit row heights D-59 requires, spacing/radii constants.

D2 — only the components Tables needs to be the real screen: WordBar, Chip (as a configurator), RootTiles, the tense/voice/iʿrāb segmented control, the 14-row list, the primary Button style. Everything else in the component table (AnswerOption, AnswerSheet, ParseAxes, SetupBar, ChartScope, StatStrip, DrillCard, QuizBar, PromptCard, TabBar) ports alongside the screen slice that actually consumes it — Q3 brings the quiz components, A1 brings SetupBar/ChartScope, A3 brings StatStrip/DrillCard, and so on.

Review tier: light — checked visually against design/midad/screenshots/ and the interactive previews, not diffed line by line. There's no domain logic here to get subtly wrong the way a conjugator can.

Exit: no hardcoded colour anywhere downstream (a grep, not just a glance); Scheherazade + Newsreader render at spec'd sizes without clipping at the largest Dynamic Type; every token has both a Paper and a Night value. Proven by E1 actually building on top of it — Track D isn't "done" in the abstract, it's done when Tables looks right.

  • availableTypes() takes its content gate as an argument, not an import of settings.

  • relevance's space → Set<…> becomes distinctAnswers → Int — only .count > 1 was ever read.
  • bab becomes a typed value with madiVowel/mudariVowel, closing Trap 3.
