01 The three quiz types

Every question in the app is one morphological fact — a root poured into a chart at a pronoun slot, or into a derived-noun pattern. What changes between quiz types is which side of that fact you're given and how you answer. That framing is what keeps this from becoming three separate quiz engines.

Turning on "Derived nouns" gives you a session that alternates between producing a derivative from a spec and classifying one you're shown — the same fact approached from both sides. Architecturally they're two shapes from a single builder (§03), which is why they cost one registry entry rather than two quiz types' worth of machinery.

What the config now controls

  • Quiz type — single-select, one per session. Mixing types in one run is deliberately deferred: it would make the results screen report two incomparable skills as one number, and the plan carries a single quizType accordingly.
  • Tense (māḍī / muḍāriʿ / amr), Voice (maʿrūf / majhūl) and Iʿrāb (marfūʿ / manṣūb / majzūm) are now first-class chip rows. Together they select the charts — you no longer pick a "chart", you pick its attributes.
  • Iʿrāb enables only when muḍāriʿ is on, exactly as you asked — it's meaningless for māḍī and amr, so it greys out rather than lying.
  • Bāb is not configurable. Each root's Form I bāb is a lexical fact, so choosing "bāb naṣara" would really be choosing a subset of roots.
  • What Identify asks is fixed at tense, voice and doer — the category picker is gone, so the only thing you configure is which words get asked about.

Consequences worth naming

  • Amr has no voice and no mood; selecting amr alone will grey out both rows. Same mechanism as Iʿrāb.
  • Some combinations are legitimately empty — majhūl of an intransitive verb, amr outside the 2nd person. The question-count line is what makes that visible before you tap Start.
  • The Tense/Voice/Iʿrāb rows apply to every quiz type: they choose the chart a word is drawn from, whether you'll be asked to read it or write it. That's the whole point of the pool model in §03.

Settled: the OS keyboard, entirely

  • No accessory row, no custom keys, no radical shortcuts. Letters and ḥarakāt both come from the system keyboard exactly as iOS presents them. We own the answer field and the grading, nothing else — the smallest possible surface, and a layout every Arabic typist already has muscle memory for.
  • Must handle A user with no Arabic keyboard installed can't answer at all — not a degraded experience, a dead end. First encounter with a writing question needs to detect it and walk them through Settings → General → Keyboards. Recorded in the spec.
  • Two costs accepted with it: ḥarakāt sit behind long-press, so entering a fully-vowelled word is slow; and typos become possible in ways a constrained keyboard would have prevented (ط for ص), so some wrong answers will be finger errors rather than sarf errors. The ḥaraka-level diff softens the second by naming exactly what differed.

Settled: fully strict grading

  • Exact match against the engine's NFC-normalised string, final ḥaraka included. The ending is the lesson, so accepting a bare يَنْصُر would teach the opposite of the app's point.
  • NFC first — the engine's strings are already normalised, so equality is safe (a hard-won invariant from the prototype: typed and templated text order ḥaraka-vs-shadda differently).
  • On a miss, diff at the character-plus-ḥaraka level and highlight the first divergence, so "one ḥaraka off" reads differently from "wrong word".
  • One slot means one written form, so a writing question has exactly one correct string — none of the multi-answer complications of the doer question.
Strictness has a consequence for mahmūz verbs. Hamza has legitimate seat variants (يَؤُمّ / يَأُمّ in some conventions). Under fully strict grading the engine's spelling is the only accepted one — fine, as long as the engine's choice matches the madrasa convention your users learned. Worth a look when the mahmūz engine lands in P2.

3b · two questions on one word

3a — pick the derivative

  • Given the verb, its form and which derivative is wanted, choose from four. The distractors are the other derivatives of the same verb plus a same-kind derivative from a neighbouring form — so every wrong option is a plausible near-miss, not filler.
  • That distractor rule is what makes it a sarf question rather than a spot-the-odd-one-out: مُسْتَخْرِج vs مُسْتَخْرَج differ by one ḥaraka, which is exactly the confusion worth drilling.
  • Options are Arabic-only. Labelling them "ism fāʿil / ism mafʿūl" would answer the question in the option list.

3b — name the derivative

  • Given a derived noun, say which kind it is and which form it comes from. I've drawn it as two questions on one word, matching the existing tense→voice→doer bundle rhythm.
  • The alternative is one question with combined options ("ism fāʿil · Form X"), which is a harder single judgement but gives you less information about which half you got wrong. Decision below.

Engine caveats the builder must respect

  • Form I maṣdar is samāʿī — not derivable, stored per root in the lexicon. Where a root has none, that question can't be asked.
  • Ism mafʿūl needs a transitive verb. Already a flag in the data, so the builder skips it rather than generating nonsense.
  • Both are just `nil` returns from the builder — the stream moves to the next word, which is the whole point of the architecture in §03.
Settled: 3b is two questions on the same word — which derivative, then which form. It matches the existing tense → voice → doer bundle rhythm, and it tells you which half you got wrong instead of collapsing both skills into one verdict.

1 · The plan selects words, not questions

Tense × voice × mood collapse into a set of ChartIDs; forms and verb types filter roots. The result is a pool of WordSpec — the same pool no matter which quiz type consumes it. This is what makes the configuration genuinely shared rather than four configs that look alike. 

// One plan. Every quiz type reads the same fields.
const plan = {
  quizTypes: ['identify', 'produce'],   // multi-select
  // no categories: identify always asks tense, voice, doer
  tenses:  ['mudari'],
  voices:  ['malum'],
  moods:   ['raf', 'nasb'],           // ignored unless mudari
  forms:   ['I', 'II', 'X'],
  verbTypes: ['salim'],
  length: { kind: 'fixed', n: 10 },
};

// charts = the cross product, computed once
function chartsFor(plan) { /* tense × voice × mood → ChartID[] */ }

// the pool every builder draws from
function* wordPool(plan, lexicon) {
  for (const root of rootsMatching(plan))
    for (const form of formsOf(root, plan))
      for (const chart of chartsFor(plan))
        for (const slot of slotsFor(chart))
          yield { root, form, chart, slot };
}

2 · A builder per quiz type, one shape out

Each builder is a pure function from a WordSpec to a Question — or to null when it can't ask anything about that word (no ism mafʿūl for an intransitive verb, no amr outside the 2nd person). The stream retries with the next word, so adding a fifth quiz type later is one file and one registry entry, touching nothing else. 

// Every builder returns this, whatever the type.
Question = {
  identity,          // WordSpec — what history records
  prompt: {
    kind: 'word'            // 1: the conjugated word
        | 'spec'            // 2: root + chart chips
        | 'derivedRequest'  // 3a: verb + form + kind
        | 'derivedWord',    // 3b: the noun itself
    ...
  },
  response: {
    kind: 'choice',  options, correctIndices
  } | {
    kind: 'arabicInput', accepted: ['يَنْصُرُ']
  },
  explanation,       // rule-based, from engine metadata
  explainPayload,    // grounding for AI Explain
};

const BUILDERS = {
  identify: buildIdentify,     // existing, unchanged
  produce:  buildProduce,      // typed Arabic
  derived:  buildDerivedNoun,  // picks shape 3a or 3b per call
};

function* questionStream(plan) {
  const pool = shuffled([...wordPool(plan)]);
  for (const spec of cycle(pool)) {
    const type = pick(plan.quizTypes);
    const q = BUILDERS[type](spec, plan);
    if (q) yield q;      // null → try the next word
  }
}

3 · Two response modes, one contract

The UI switches on response.kind and nothing else: a choice list or an Arabic input with its keyboard. Grading lives with the response, not with the quiz type, so a future "choose the correct spelling" question would reuse the choice renderer with a produce-style prompt at no cost. 

function grade(question, given) {
  const r = question.response;
  if (r.kind === 'choice')
    return setEquals(given, r.correctIndices);

  // arabicInput: NFC first — the engine's strings are
  // already normalised, so equality is safe. Fully
  // strict: the final ḥaraka counts.
  const typed = nfc(given);
  if (r.accepted.some((a) => nfc(a) === typed))
    return { correct: true };

  // wrong → say *how* wrong, not just "no"
  return { correct: false, diff: firstDivergence(typed, r.accepted[0]) };
}

4 · History stays one table

Because every question carries the same WordSpec identity, an answer record is the same shape for all three types — the only difference is what lands in the "what you gave" column. Stats can then compare your recognition of muḍāriʿ majhūl against your production of it, which is a far better weak-spot signal than either alone. 

AnswerRecord {
  // identity — identical across all quiz types
  quizType, category, form, verbType,
  chart, rootKey, slot,

  // what happened
  given:    ['3fs'] | 'يَنْصَرُ',
  expected: ['3fs','2ms'] | 'يَنْصُرُ',
  wasCorrect: false,
  answeredAt,
}
One thing to decide later: production questions are strictly harder than recognition ones, so mixing them in a single accuracy number flatters or punishes depending on the mix. Stats probably need to report them separately rather than as one percentage.
Approved and written into the plan. §A.7 now carries WordSpec, QuizPlan with tense/voice/mood attributes resolving to charts, the QuestionBuilder protocol with one builder per type, the two-case Response enum, and the note that bāb is deliberately absent from the plan. A.10's module layout and B.3's AnswerRecord were updated to match — including the free-tier 30-day summary and a note that production and recognition accuracy should be reported separately, since mixing them into one percentage makes the number move with the mix rather than with skill.

Settled

  • Search matches root letters and English gloss only. No reverse index over generated forms — typing يَنْصُرُونَ won't find its chart. Simple, instant, and no build cost; the spec records the fuller version as deferred rather than rejected, in case reading practice becomes a goal later.
