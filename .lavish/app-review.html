01 The four quiz types

Every question in the app is one morphological fact — a root poured into a chart at a pronoun slot. What changes between quiz types is which side of that fact you're given and how you answer. Laying them out on those two axes is what keeps this from becoming four separate quiz engines.

Types 2 and 4 are the same question with a different cue. Both ask you to produce a word; one describes the target in grammatical labels, the other in English meaning. Type 3 is the same again with a derived noun as the target instead of a chart cell. That collapses four quiz types into two directions (recognise ↔ produce) × two cues (grammatical ↔ English) × two targets (chart cell ↔ derived noun) — which is exactly what the architecture in §04 encodes.

What the config now controls

  • Quiz type — multi-select. Turn on two and the quiz alternates between them, so one session can mix reading and writing.
  • Tense (māḍī / muḍāriʿ / amr), Voice (maʿrūf / majhūl) and Iʿrāb (marfūʿ / manṣūb / majzūm) are now first-class chip rows. Together they select the charts — you no longer pick a "chart", you pick its attributes.
  • Iʿrāb enables only when muḍāriʿ is on, exactly as you asked — it's meaningless for māḍī and amr, so it greys out rather than lying.
  • Bāb is not configurable. Each root's Form I bāb is a lexical fact, so choosing "bāb naṣara" would really be choosing a subset of roots. Bāb stays a question category ("which bāb is this?"), never a filter.
  • "What to identify" only applies to type 1 — it dims when Identify is off, because "wazn" isn't a thing you can ask of a writing question.

Consequences worth naming

  • Amr has no voice and no mood; selecting amr alone will grey out both rows. Same mechanism as Iʿrāb.
  • Some combinations are legitimately empty — majhūl of an intransitive verb, amr outside the 2nd person. The question-count line is what makes that visible before you tap Start.
  • The old flat "Custom" categories list is now split: what to identify (type 1) versus which words to draw from (all types).

Why a custom keyboard

  • The iOS Arabic keyboard puts ḥarakāt behind long-press. A drill about ḥarakāt cannot make ḥarakāt the hardest thing to type — the interface would be testing dexterity, not sarf.
  • Offering the three radicals as highlighted keys plus the small closed set of prefix/suffix letters turns the task into what it actually is: assembling a known template, not free writing.
  • It also constrains errors to meaningful ones. You can't typo ط for ص; every mistake you can make is a sarf mistake, which is what makes the diff feedback teachable.

Grading

  • Compare NFC-normalised strings — the engine's answer is already normalised, so equality is safe (a hard-won invariant from the prototype).
  • On a miss, diff at the character-plus-ḥaraka level and highlight the first divergence. "One ḥaraka off" is a completely different message from "wrong word", and the app knows which it is.
  • Several slots share a written form, but the reverse — one slot, one form — is unambiguous, so a produce question has exactly one correct string. No multi-answer complications here.

Type 3 — derived nouns

  • The engine already generates ism fāʿil, ism mafʿūl and maṣdar patterns per form, so the answer is engine-produced like everything else.
  • Two real caveats: Form I maṣdar is samāʿī — not derivable, stored per root in the lexicon — and ism mafʿūl needs a transitive verb. Both are already flags in the data, so the builder skips what it can't ask.
  • Keyboard shifts from "prefixes & endings" to pattern letters (ا م ت و ي) — the letters the mushtaqq patterns actually add.

Type 4 — English → Arabic

  • The cue is the contextual meaning the MeaningService already produces for feedback: "they two (f) are being helped". Nothing new to author — the sentence that currently teaches becomes the sentence that tests.
  • Problem "he helped" doesn't identify a root — نَصَرَ, أَعَانَ and سَاعَدَ all mean it. I've shown the root alongside the English, which makes the question answerable but softens it. The decision below.
  • Your example phrasing, "he one male helped", suggests you want the pronoun spelled out rather than natural English. Worth deciding whether the cue reads naturally or grammatically — see below.

03 Architecture — how four quiz types stay one engine

Your constraint: serve different quiz types while keeping configuration identical across them. The move that makes this work is to stop thinking of the config as describing a quiz, and start thinking of it as describing a pool of words. Everything else follows.

1 · The plan selects words, not questions

Tense × voice × mood collapse into a set of ChartIDs; forms and verb types filter roots. The result is a pool of WordSpec — the same pool no matter which quiz type consumes it. This is what makes the configuration genuinely shared rather than four configs that look alike. 

// One plan. Every quiz type reads the same fields.
const plan = {
  quizTypes: ['identify', 'produce'],   // multi-select
  categories: ['tense', 'doer'],       // identify only
  tenses:  ['mudari'],
  voices:  ['malum'],
  moods:   ['raf', 'nasb'],           // ignored unless mudari
  forms:   ['I', 'II', 'X'],
  verbTypes: ['salim'],
  length: { kind: 'fixed', n: 10 },
};

// charts = the cross product, computed once
function chartsFor(plan) { /* tense × voice × mood → ChartID[] */ }

// the pool every builder draws from
function* wordPool(plan, lexicon) {
  for (const root of rootsMatching(plan))
    for (const form of formsOf(root, plan))
      for (const chart of chartsFor(plan))
        for (const slot of slotsFor(chart))
          yield { root, form, chart, slot };
}

2 · A builder per quiz type, one shape out

Each builder is a pure function from a WordSpec to a Question — or to null when it can't ask anything about that word (no ism mafʿūl for an intransitive verb, no amr outside the 2nd person). The stream retries with the next word, so adding a fifth quiz type later is one file and one registry entry, touching nothing else. 

// Every builder returns this, whatever the type.
Question = {
  identity,          // WordSpec — what history records
  prompt: {
    kind: 'word' | 'spec' | 'english' | 'derived',
    ...                // what the card renders
  },
  response: {
    kind: 'choice',  options, correctIndices
  } | {
    kind: 'arabicInput', accepted: ['يَنْصُرُ'],
    keyboard: { radicals, affixes }
  },
  explanation,       // rule-based, from engine metadata
  explainPayload,    // grounding for AI Explain
};

const BUILDERS = {
  identify:    buildIdentify,     // existing, unchanged
  produce:     buildProduce,      // grammatical cue
  derived:     buildDerivedNoun,
  translate:   buildTranslate,    // english cue
};

function* questionStream(plan) {
  const pool = shuffled([...wordPool(plan)]);
  for (const spec of cycle(pool)) {
    const type = pick(plan.quizTypes);
    const q = BUILDERS[type](spec, plan);
    if (q) yield q;      // null → try the next word
  }
}

3 · Two response modes, one contract

The UI switches on response.kind and nothing else: a choice list or an Arabic input with its keyboard. Grading lives with the response, not with the quiz type, so a future "choose the correct spelling" question would reuse the choice renderer with a produce-style prompt at no cost. 

function grade(question, given) {
  const r = question.response;
  if (r.kind === 'choice')
    return setEquals(given, r.correctIndices);

  // arabicInput: NFC first — the engine's strings
  // are already normalised, so equality is safe.
  const typed = nfc(given);
  if (r.accepted.some((a) => nfc(a) === typed))
    return { correct: true };

  // wrong → say *how* wrong, not just "no"
  return { correct: false, diff: firstDivergence(typed, r.accepted[0]) };
}

4 · History stays one table

Because every question carries the same WordSpec identity, an answer record is the same shape for all four types — the only difference is what lands in the "what you gave" column. Stats can then compare your recognition of muḍāriʿ majhūl against your production of it, which is a far better weak-spot signal than either alone. 

AnswerRecord {
  // identity — identical across all quiz types
  quizType, category, form, verbType,
  chart, rootKey, slot,

  // what happened
  given:    ['3fs'] | 'يَنْصَرُ',
  expected: ['3fs','2ms'] | 'يَنْصُرُ',
  wasCorrect: false,
  answeredAt,
}
One thing to decide later: production questions are strictly harder than recognition ones, so mixing them in a single accuracy number flatters or punishes depending on the mix. Stats probably need to report them separately rather than as one percentage.

Settled

  • Explain appears only on wrong answers, for free and Pro alike. It reads as remediation rather than an upsell, and it halves the exposure of the trial counter.
  • No skip button — guessing is part of the drill, and the answer is revealed immediately anyway.
  • "See full table" stays on both correct and incorrect feedback; it's free and it's study, not sales.

Consequence to watch

  • Explain is now invisible to a user who answers well — which is exactly the user least likely to subscribe on the strength of it. If conversion matters more than restraint, the fallback is a single Explain entry on the results screen for any question, right or wrong.

More tab — unchanged this round

  • Detailed stats (Pro) · quiz history (Pro) · subscription · default quiz length · Arabic text size · appearance · restore · privacy.
