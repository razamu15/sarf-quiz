01 The bug you found is bigger than the identify quiz

You selected muḍāriʿ only and the quiz kept asking "what kind of verb is this?". I measured it — a muḍāriʿ · maʿlūm · rafʿ configuration produces 30 questions, of which 18 are free points:

8tense questions, every answer مُضَارِع
10voice questions, every answer مَعْلُوم
12doer questions — the only ones that still require reading the word

The count line compounds it: it reports 798 possible questions for that configuration because it multiplies the word pool by three categories. The honest number is 266 — the doer questions. Everything else is a coin with one face.

The general rule A question is dead when the property it asks about is constant across the pool the plan admits. Tense is dead when the plan admits one tense. Voice is dead when it admits one voice — or when every root in scope is intransitive, so the majhūl never materialises. "Which form is this derivative from?" is dead when the plan admits one form. It is one rule, and it explains every case including the two we already handle by hand.

We already do this — three times, three different ways

That's the real finding. Relevance is already enforced at three levels, each invented separately, none of them named:

LevelQuestion it answersWhere it lives today
Plan Is this question worth asking at all, given the whole configuration? Nowhere. This is the gap you found.
Word Can this word support this question? Ad hoc, three places: the voice builder retries until it finds a word whose opposite voice exists; the iʿrāb builder skips slots where the three states look identical; buildDrill skips lāzim non-sound words because their wazn fallback doesn't exist.
Option Are the distractors genuinely wrong? Done well: doer questions promote same-form pronouns to correct answers; 3a draws distractors from the verb's other derivatives.

So the fix isn't to bolt a special case onto the tense question. It's to give the plan level the same first-class treatment the option level already has — and, while we're there, to fold the scattered word-level retries into the same shape.

02 Proposed: every question declares what it discriminates

A question kind becomes a small object that knows three things: what property it tests, how to compute that property's answer space for a given plan, and how to build itself. If the answer space has fewer than two members, the question never enters the quiz. 

// One entry per question kind. `space` returns the set of distinct answers
// this question could have under the given plan. Two or more → live.
const QUESTION_KINDS = [
  {
    id: 'tense', quizType: 'identify',
    space: (plan) => new Set(chartsFor(plan).map((c) => CHARTS[c].tense)),
    make: makeTenseQuestion,
  },
  {
    id: 'voice', quizType: 'identify',
    // not just the plan's voices: a pool of intransitive roots has no
    // majhūl however many boxes are ticked
    space: (plan, pool) => new Set(pool.map((w) => CHARTS[w.chart].voice)),
    make: makeVoiceQuestion,
  },
  {
    id: 'doer', quizType: 'identify',
    // 14 slots; only degenerate if a plan could pin one, which it can't
    space: (plan) => new Set(chartsFor(plan).flatMap(slotsFor)),
    make: makeDoerQuestion,
  },
  {
    id: 'derivedKind', quizType: 'derived',
    space: (plan, pool) => new Set(pool.flatMap((w) => w.kinds)),
    make: makeDerivedKindQuestion,
  },
  {
    id: 'derivedForm', quizType: 'derived',
    space: (plan) => new Set(plan.forms),      // one form ticked → dead
    make: makeDerivedFormQuestion,
  },
  {
    id: 'produce', quizType: 'produce',
    space: () => INFINITE,                    // writing is never a coin flip
    make: makeProduceQuestion,
  },
];

// Computed once when the plan changes — not per question.
function activeKinds(plan, pool) {
  return QUESTION_KINDS
    .filter((k) => k.quizType === plan.quizType)
    .filter((k) => k.space(plan, pool).size > 1);
}

One pass, three answers

The pool walk already exists — possibleQuestions() does it to print the count line. The same walk now yields three things at once, which is why this costs almost nothing:

  • Which questions are live — the answer spaces.
  • An honest count — pool size × live kinds, instead of × 3 regardless.
  • Something to tell the user — Practice can name what this configuration will actually ask.

Most spaces are cheap: tense and iʿrāb are computed from the chart list alone (nine items), forms from the plan directly. Only voice needs the pool, because transitivity is a property of roots rather than of the configuration. Worth memoising per plan on iOS once the lexicon is in the hundreds — flagged, not urgent.

The same idea fixes the drill bundle

Home drills are hardcoded as three questions per word — tense, then voice-or-wazn, then doer — with a special case that skips lāzim non-sound words because the wazn fallback only exists for sound verbs. Under the new model a bundle is simply the active kinds applied to one word. The special case dissolves: a word that can only support two questions gives two, and the drill draws another word to reach its length.

Two ways to build it — and why I'd pick the second

A · Gate on the plan only

Each question kind declares which plan fields it depends on; drop it when that field has one value.

Cheap, fully static, no pool walk. But it can't see that a pool of intransitive roots has no majhūl, or that the only selected root lacks a maṣdar — so degenerate questions still slip through for content reasons rather than configuration reasons.

Not enough on its own

B · Answer space over the actual pool

Each kind computes the set of answers it could have, over the cheapest domain that suffices — the chart list, the plan's forms, or the pool where it genuinely needs it.

Catches configuration and content degeneracy in one mechanism, reuses the pool walk we already do for the count, and yields the "this setup asks…" copy for free.

03 Full history for everyone, from the first build

Straightforward, and I agree with it — but it reverses a decision from the last review, so it's worth naming: we settled on a rolling 30-day summary for free users (daily counts and accuracy, no per-answer rows), and that is what PRODUCT_SPEC §5.4 and js/stats.js say today. The new position is: store everything for everyone, gate the reading of it.

Why this is the better call Data you didn't keep can't be backfilled. Under the summary model, a user who subscribes in March gets a dashboard that starts in March. Under this model they get every answer they ever gave — which is both a better product and the strongest upsell the app has: "2,341 answers are waiting to be analysed." You can only say that if you kept them.

04 Things you didn't mention that this forces

1 · localStorage will not hold it An answer record is roughly 150 bytes of JSON. A committed user doing 100 questions a day fills ~5.5 MB in a year — and localStorage caps around 5 MB, silently throwing once full. The prototype needs IndexedDB, or a cap with a documented eviction rule. On iOS SwiftData doesn't care, so this is a prototype-only problem — but it will bite during testing, not after.
2 · Keeping everything means being able to delete everything Storing a complete behavioural record for free users changes the privacy posture. It stays on-device and un-synced for free, so the App Privacy label is still "data not collected" — but Settings needs a real Delete my history, and ideally an export. Cheap to build now, awkward to retrofit after review feedback asks for it.
3 · Does a free user's history sync to iCloud? If yes, free users get cross-device continuity and their history survives a reinstall — and Apple hosts it at your cost. If no, a free user who reinstalls loses the very history that would have converted them. My instinct: local for free, CloudKit for Pro, and say so on the paywall ("your history, on every device"). It's a decision, not a detail.
4 · The count line is wrong today, independently of all this possibleQuestions() multiplies the pool by three categories whatever the configuration. Even before the relevance work lands, that number is overstated for any narrowed plan. Same fix, same commit.
5 · Stats will compare unlike things With the question mix varying by configuration, a raw accuracy number moves when your habits change, not just your skill — a week of doer-only drills reads as a slump. Every record already carries its category, so the fix is presentational: report accuracy per question kind, and keep production (write-the-word) separate from recognition, which we already agreed.
6 · Weak-spot drills get this for free The Pro feature builds a configuration from your worst cells — and a config that narrow is exactly the degenerate case. With relevance in place, a weak-spot drill on "muḍāriʿ majhūl, Form VII" automatically asks only the questions that still discriminate. Without it, that feature would have shipped mostly free points.
