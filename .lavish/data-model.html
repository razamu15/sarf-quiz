01 The shape of the model

Five layers, and one rule that explains the whole arrangement: a word is never stored, it is a join. Everything on the left of the join is content or grammar; everything on the right is a projection of the word that came out.

1 · Closed vocabulary

The enums. Nothing here grows with content — ChartID, PronounSlot, FormID, VerbType, Bāb and friends. They are the join keys the rest of the system uses instead of strings.

2 · Lexicon (content)

Root and its per-form usage. The only thing that grows per root added. The one layer that would ship as JSON in Swift.

3 · Grammar (code-as-data)

Stems, ending tables, derived-noun templates, form metadata — written out explicitly per verb type so each chart is auditable against the paper handout.

4 · Engines

One conjugator per verb type behind a single protocol, plus the service that routes to them by root.type. Two of seven exist today.

5 · Runtime

Plan → analysis → question kinds → questions → answers → history. Every one of these is a projection of the same word identity.

+ Display

Eleven label maps keyed by the enums. Deliberately separated from grammar in v2 — engine data and display strings never share a type again.

The identity that ties it together WordSpec — (rootKey, form, chart, slot), or (rootKey, form, derived) for a derived noun. It is the composite key of the generated word, and it is what Question carries, what AnswerRecord stores, and what every stat later slices by. In the prototype it exists as loose fields rather than a named type — see §06 and §13.

The practical consequence Only seven types in this whole system are ever instantiated per user action — QuizPlan, PoolProfile, ChartTemplate, Question, AnswerOption, Cue, Grade — plus the two persisted records. 06 Why Question and AnswerRecord overlap ◆ answers your diagram-2 note

You spotted it correctly: eight fields appear on both — category, rootKey, form, chart, slot, derivedKind, verbType, word. That is not an accident and it is not (yet) a mistake, but it is currently unenforced, which is the real problem.

The relationship is projection, not reference

// what exists today, spread across two files:
// quiz-service.js
function verbFields(v, category) {
  return { category, formId, verbType, chartId, rootKey, slot, word, gloss, fullMeaning };
}
// history.js — writes the SAME identity again, by hand
function recordAnswer(question, { correct, given }) {
  current.answers.push({ quizType, category, form, verbType, chart, rootKey, slot, derivedKind, word, ... });
}

Three reasons the copy is deliberate, in order of how much they matter:

  1. Records must survive content change. If AnswerRecord held a pointer (or a SwiftData relationship) to Root, then editing a gloss or deleting a root in 2027 would silently rewrite — or dangle — what a 2026 answer says it asked. Copying the identity freezes the question as it was actually put to the user. This is the load-bearing reason.
  2. Different lifetimes. A Question lives for one screen and is discarded; an AnswerRecord is permanent. Objects with a 30-second lifetime and objects with a 10-year lifetime should not be the same object.
  3. Stats query records directly, with no join. accuracyBy('form') groups a flat array. On SwiftData, keeping aggregates off relationship traversal is what keeps the dashboard cheap as history grows.
What is actually wrong with it today The eight fields are written out three times — verbFields(), derivedFields() and recordAnswer() — and nothing checks that they agree. Add a field to the identity and you must remember all three sites; miss one and history quietly loses a dimension that stats will later need.

The fix is the same one §13 names: make WordSpec a real type and have both embed it. Question = WordSpec + presentation, AnswerRecord = WordSpec + outcome. The overlap stays — it should — but it becomes one definition used twice instead of three hand-kept copies. 
// the shape worth porting instead
struct WordSpec { rootKey; form; chart; slot; derived; word }

struct Question    { let identity: WordSpec; let prompt; response; explanation }
struct AnswerRecord { let identity: WordSpec; let expected; given; correct; answeredAt }

The one that was more than a rename

Naming the v object was the pick with structural payoff (§06), so it got a real definition rather than just a new label — the single source of truth those three hand-kept copies should eventually share: 

/**
 * WordSpec — the identity of one generated word, and the single most reused
 * shape in the system. A Question embeds it; an AnswerRecord copies it. It is
 * carried as a KEY (rootKey string), never as a Root object reference, so a
 * stored record still says what it asked after the lexicon is edited.
 *
 * Today it is a plain object built by randomWordSpec() and flattened onto
 * questions by specFields(); history.js writes the same fields again by hand.
 * Making those three sites share one definition is the open item.
 */
@typedef  {object}   WordSpec
@property {object}   root          // the Root it came from
@property {string}   formId        // FormID — 'I' … 'X'
@property {string}   chartId       // ChartID — null for derived nouns
@property {string}   slot          // PronounSlot — null for derived nouns
@property {string}   word          // the generated result, NFC-normalised
@property {boolean} [hasVoicePair] // drills only: the majhūl also exists
Two judgement calls I made inside your picks The draw helpers came along. You renamed the method to buildFromPool; leaving drawVoice/drawMood/drawDerived behind would have kept the word you were removing. They became buildVoice/buildMood/buildDerived — "FromPool" would have been noise on three private helpers that only ever draw from the pool.

The cue-card and cue-spec CSS classes were left alone. Renaming the data field is a model change; renaming style hooks is churn across two stylesheets, and "cue card" is still an accurate name for what that card looks like. Say the word if you want them aligned.
One thing the tests caught The cue → target pass initially missed smoke.mjs, and the assertion "every produce question carries a cue and one accepted answer" failed immediately — 215 passed, 1 failed. Fixed and green. Worth noting because it is exactly the class of half-applied rename that a weaker suite lets through silently.

13 Three things this inventory exposes

WordSpec — half fixed

PARTIAL It now has a name and a @typedef, so the shape is stated once. But the fields are still written out three times — specFields(), derivedFields(), recordAnswer() — and nothing checks they agree.

Naming it was the prerequisite; collapsing the three copies into one embedded value is the remaining work, and it should land before the Swift port freezes the shape.

Two grammars, one ENDINGS

MudaafConjugator imports ENDINGS and PREFIX_LETTERS from salim-grammar.js. Correct — the endings genuinely are shared — but the file name says otherwise.

Five more engines will import it too. Worth a shared endings.js before P2 finishes rather than after.

The plan is stored twice

SessionRecord.plan holds a deep copy of the QuizPlan, and every AnswerRecord under it repeats the identity fields.
