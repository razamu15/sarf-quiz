01 The rule every field below obeys

Each object knows only its left neighbour

QuizWordPool takes a plan and never hears of questions. Question is built from a drawn WordSpec and never hears of runs. Answer holds a question and never hears of storage.

The one place this could break is QuizRun writing history — decision D3.

Absence is a value, never a stand-in

mood is null outside the muḍāriʿ. bab is null for mazīd forms. slot is null for derived-noun and bāb questions. divergeAt is null for choice answers, not -1. total is null for an endless run, not Infinity.

Every one of those nulls means “this question does not apply here”, and a reader can tell.

03 QuizPlan — what to draw from

/**
 * The configuration of a session. It describes A POOL OF WORDS, not a set of
 * questions — which is what lets one configuration serve all four quiz types.
 *
 * Called by: the Practice screen (from its chips), drills.js (from a preset),
 * and planFrom() below (replaying a stored session).
 *
 * NOTE — a tracked decision, not an oversight (A1a · F3): a plan can narrow
 * WHICH WORDS are drawn, but not WHICH QUESTIONS are asked about them. That is
 * relevance()'s job, from what the pool actually contains. The consequence is
 * that a weak-spot drill on "doer × Form II" restricts the forms and then takes
 * whatever kinds relevance offers, so it is diluted by the questions you were
 * not weak on. Chosen deliberately in Aug 2026. Revisiting it means an optional
 * `questionKinds` here that INTERSECTS with the live kinds — able to narrow,
 * never to resurrect a kind relevance retired.
 */
export function quizPlan({ quizType, tenses, voices, moods, forms, types, count }) {
  return Object.freeze({
    quizType,   // one per session. Never a list — the results screen must not
                // average two incomparable skills into one number.
    tenses, voices,
    moods,      // meaningful only when 'mudari' is in tenses. Not nulled here:
                // planCharts() ignores it, and keeping the user's selection means
                // re-ticking muḍāriʿ restores what they had.
    forms,
    types,      // ENGINE types: 'ajwaf_waw'. Never group names. The UI expands a
                // pick ONCE via verbTypesInGroup(); glossary turns a stored type
                // back into a label. Carrying group names into data is what
                // silently killed the muʿtall drill.
    count,      // 5 | 10 | 20 | 'endless'
  });
}

/** tense × voice × mood → the chart shapes this plan admits. */
export function planCharts(plan) /* → [{tense, voice, mood}] */

/**
 * Rebuild a plan from a stored session (Q24). VALIDATES rather than trusts:
 * a plan written by an older release can name a verb type that was since split,
 * a quizType that was renamed, or a form whose content has gone.
 *
 * Returns { plan, dropped } — never a silently narrowed plan. The screen says
 * "3 verb types from this session are no longer available" instead of quietly
 * running a smaller quiz than the one being replayed.
 */
export function planFrom(stored) /* → { plan, dropped: string[] } */

04 QuizWordPool — what can be drawn

The object that was genuinely missing. Today three functions walk the same candidates for three different answers — poolProfile() for what varies, conjugatable() for what exists, randomWordSpec() for a draw — and none of them is a thing you can hold. 

/**
 * Every word the plan admits, resolved in ONE walk that answers three things:
 * how many real cells exist (the count under Start), which properties actually
 * vary (the entire input to relevance), and how to draw one at random.
 *
 * Called by: QuizRun (to draw), the Practice screen (count + "This setup asks"),
 * and relevance() — which now takes a POOL rather than a plan, because a
 * question dies from what the pool CONTAINS, not from what was ticked.
 */
export function wordPool(plan) {
  const charts = planCharts(plan);
  const candidates = lexiconCandidates(plan.types, plan.forms)
    .filter((c) => FORM_META[c.formId].conjugable);   // Form IX is recognition-only

  const varies = { tenses: new Set(), voices: new Set(), moods: new Set(),
                   slots: new Set(), forms: new Set(), babs: new Set(),
                   derivedKinds: new Set(), derivedForms: new Set() };
  let cells = 0;

  if (plan.quizType === 'derived') {
    // A different unit of account: the askable thing is a DERIVATIVE, not a
    // chart cell. Same object, different walk — the callers only need the
    // count and `varies`, and the two fill disjoint keys of it.
    for (const c of candidates)
      for (const kind of derivativesOf(c.root, c.formId)) {
        cells++; varies.derivedKinds.add(kind); varies.derivedForms.add(c.formId);
      }
  } else {
    for (const c of candidates)
      for (const chart of charts)
        for (const slot of slotsFor(chart.tense)) {
          if (!conjugate(specOf(c, chart), slot)) continue;   // nils excluded — the count
          cells++;                                            // is REAL cells, so no
          varies.tenses.add(chart.tense);                     // majhūl of a lāzim verb
          varies.voices.add(chart.voice);                     // is ever promised
          if (chart.mood) varies.moods.add(chart.mood);
          varies.slots.add(slot);
          varies.forms.add(c.formId);
          // The bāb question reads the ʿayn vowel off a citation, which only
          // sits in plain view on a sound Form I verb.
          if (c.formId === 'I' && c.root.type === 'salim') varies.babs.add(c.root.forms.I.bab);
        }
  }

  return { plan, candidates, charts, cells, varies, draw };
}
One thing this walk costs, and why it is still right It conjugates every cell to count it — ~4,900 calls for the mazīd preset. That is milliseconds in the browser and it buys an honest count: nils are excluded, so “≈ 1,422 possible questions” never promises a majhūl that a lāzim verb cannot form. The alternative — multiplying dimensions — is what made a muḍāriʿ-only plan claim 798 questions when 266 of them meant anything. If it ever gets slow, the fix is caching the pool per plan, not estimating.

05 Question — four named parts

Today this is a flat object of ~15 keys in which identity, display, grading and explanation are indistinguishable, and the screen picks out the three or four it cares about — including by inferring which card to render from which keys happen to be present. 

Question {
  quizType, category,   // WHAT is being asked. Carried, never inferred from shape —
                        // inferring it is what silently misfiled new quiz types.
  identity: WordSpec,   // WHAT WORD it is about (§02)
  prompt:   Prompt,     // WHAT THE CARD RENDERS — tagged (below)
  response: Response,   // HOW YOU ANSWER, and what counts as correct
  feedback: { meaning, explanation },   // shown after. Tips are COMPUTED at render
                        // time from (question, answer) — they depend on what you got
                        // wrong, which is not known when the question is built.
}

Prompt — six kinds, and they are not the four quiz types

// The `kind` tag exists because the screen currently INFERS the card from
// shape:  response === 'input' ? cueCard : meaningPrompt ? meaningCard : wordCard
// — which is a chain of coincidences, and the fragile kind. Six kinds against
// four quiz types is the proof that prompt shape is its own axis.
Prompt =
  | { kind: 'word',           text, gloss }              // identify — the conjugated word
  | { kind: 'citation',       text, gloss }              // bāb — نَصَرَ يَنْصُرُ, two tenses
  | { kind: 'spec',           radicals, gloss, chips }   // produce — the cue card
  | { kind: 'meaning',        meaning, radicals }        // fromMeaning — English only
  | { kind: 'derivedRequest', verb, chips }              // 3a — the verb + which derivative
  | { kind: 'derivedWord',    text }                     // 3b — the derivative itself

// The 'meaning' kind is the one with a live hazard: it must NEVER carry the
// Arabic word, because the word is the answer. Making it its own type with no
// `text` field means the mistake cannot be made rather than must be remembered.

Response — two modes, and correctness stops being positional

Response =
  | { mode: 'choice', options: [{ ar, en, valueKey }], correct: Set<valueKey> }
  | { mode: 'input',  accepted: [string] }

// THE CHANGE THAT MATTERS: `correct` is a set of VALUE KEYS, not indices.
// Today it is `correctIndices: [i, …]`, so correctness is a property of where
// a button sits. Re-shuffle the options and the answer key is wrong. Value keys
// are what history already stores, so this also removes the last translation
// step between grading and the record.
//
// `multiSelect` is DERIVED — correct.size > 1 — not stored. One fact, one place.
// The UI contract reads it directly: size 1 resolves on first tap, size > 1
// shows "Select all that apply" and a Check button.

06 Answer — the history row

/**
 * One thing recorded. Produced ONCE, appended to the run, and written to
 * storage unchanged. It replaces the separate shape history.js builds today.
 */
Answer {
  question:  Question,      // EMBEDDED WHOLE (A1a · D1). Its identity is already a
                            // flat key-based projection, so embedding reintroduces no
                            // reference. And Q21/Q23 need the options and the prompt,
                            // which no reconstruction can recover — they were sampled
                            // and shuffled from a random draw at build time.
  given:     [string],       // value keys picked, or [the typed string]
  expected:  [string],       // value keys required, or [the engine's own word]
  correct:   boolean,
  divergeAt: number | null, // input only: first differing index. null for choice —
                            // an absence, not a 0 and not a -1.
  answeredAt,
}
Why given and expected stay flat rather than nesting in the question They are the only fields that are about the user rather than about the question — and they are what Q20 (confusion pairs) and every recognition tip read. Keeping them at the top makes “gave 2ms, wanted 3fs” a one-line read on the record, and it is why tipsFor(question, answer) can fire on the confusion rather than merely on the word.

07 The three functions that carry the logic

grade() — the boundary that does not currently exist

/**
 * question + what the user did → an Answer. ONE function, both modes.
 *
 * Called by: QuizRun.answer(), and nothing else. The screen renders an Answer;
 * it never computes one. That is the whole point — today the choice branch of
 * this lives in app.js's answerChoice() and history.js re-derives `expected`
 * from the question a third time.
 *
 * Grading keys on RESPONSE MODE, not quiz type: nine of the ten question kinds
 * grade identically, and the plan already anticipates a produce-style prompt
 * with a choice response ("choose the correct spelling").
 */
export function grade(question, given) {
  const base = { question, answeredAt: nowISO() };

  if (question.response.mode === 'choice') {
    const expected = [...question.response.correct];
    return { ...base, given, expected, divergeAt: null,
             correct: given.length === expected.length
                      && given.every((v) => question.response.correct.has(v)) };
  }

  // Strict, final ḥaraka included — the ending IS the lesson. The engine's
  // string is already NFC; the typed one may not be.
  const typed = given[0].normalize('NFC').trim();
  const expected = question.response.accepted[0];
  if (typed === expected)
    return { ...base, given: [typed], expected: [expected], correct: true, divergeAt: null };

  // WHERE it diverged, so feedback can say "one ḥaraka off" rather than "wrong".
  // Walked over GRAPHEME CLUSTERS, not code units: a letter plus its ḥaraka plus
  // a shadda is one cluster, and an index inside it points at half a ḍamma.
  return { ...base, given: [typed], expected: [expected], correct: false,
           divergeAt: firstDifferingCluster(typed, expected) };
}
A live bug hiding in that last line — reproduced, not suspected

Today gradeInput walks code units and markAt() underlines text[at], a single UTF-16 unit. Typing تُنْصَرَانَ for تُنْصَرَانِ — one ḥaraka off, the commonest possible miss: 

divergeAt (code units) = 10 of 11
char at that index     = "َ"  → U+064E   ← a BARE FATḤA, detached from its ن

clusters               = 6  ["تُ","نْ","صَ","رَ","ا","نَ"]
divergeAt (clusters)   = 5  → "نَ"      ← the letter WITH its ḥaraka

So the feedback that is supposed to say “you were one ḥaraka off, here” underlines a floating diacritic. Intl.Segmenter clusters fix it — and it is the same fix Compare needs for its letter-level diff, so the cluster helper gets one owner, used by grading and by the diff.

QuizRun.answer() and advance()

class QuizRun {
  // #source is an array (fixed count) OR an iterator (endless). One field, two
  // shapes, because "how many are left" is the only thing that differs and the
  // screen asks that through `total`.
  #source; #served = [];
  plan; pool; mode; index = 0; answers = [];

  get current() { return this.#served[this.index]; }
  get total()   { return this.isEndless ? null : this.#source.length; }
                    // null, not Infinity: "there is no total" is a different
                    // fact from "the total is very large", and the progress bar
                    // needs to tell them apart.

  answer(given) {
    const a = grade(this.current, given);
    this.answers.push(a);
    return a;                    // ← who persists this is decision D3
  }

  advance() {
    if (this.isEndless) {
      const next = this.#source.next();
      if (next.done) return false;   // the pool ran dry — a real end, even here
      this.#served.push(next.value);
    }
    if (this.index + 1 >= this.#served.length) return false;
    this.index++;
    return true;
  }

  finish() { return { plan: this.plan, mode: this.mode,
                     startedAt: this.startedAt, endedAt: nowISO(),
                     answers: this.answers }; }
}

store.rowFor() — the only place that knows about query columns

/**
 * A1a · D1. The domain object embeds the question; THIS function alone derives
 * the flat columns the dashboard groups by. The index is a copy, in one place,
 * rebuildable from the embedded question at any time — an index, not a second
 * source of truth.
 *
 * In the prototype this is nearly a no-op (localStorage takes JSON). In Swift
 * the same function fills the @Model's stored properties, because #Predicate
 * cannot index into an embedded value. Same move LexiconService already makes:
 * one type knows where the data lives.
 */
function rowFor(answer) {
  const { identity, quizType, category } = answer.question;
  return {
    ...identity,        // rootKey formId verbType bab tense voice mood slot derivedKind
    quizType, category, // Q7, Q14, Q15
    correct: answer.correct,
    answeredAt: answer.answeredAt,
    answer,             // ← the whole thing, for Q21 and Q23
  };
}

10 Decisions

D1 · Where does the generated word live?
Today word is a top-level field meaning different things per type: the prompt content for identify and derived, the answer for produce and fromMeaning. That ambiguity is worth killing, but there are two ways.
D2 · Is citation its own prompt kind?
The bāb question shows نَصَرَ يَنْصُرُ — two words, both tenses — where every other identify question shows one. It renders the same as word today.
D3 · Who writes an answer to storage?
The one place the “each object knows only its left neighbour” rule could break. Endless sessions matter here: they can run indefinitely, so a session only written at the end is a session a crash loses.

The parity proof

A refactor this size needed better evidence than "the tests still pass", so before touching anything I snapshotted every word, derived noun, citation and meaning the engine can produce — 20,252 of them — and diffed it after. Zero differences. The 112 hand-typed v1-parity assertions are also byte-identical. Not one generated word changed.

One bug found in this design, during implementation

A Set does not survive JSON §05 specified response.correct as a Set of value keys. But an Answer embeds its whole Question and is written to storage unchanged — and JSON.stringify(new Set(['3fs'])) is {}. Every replayed session would have shown no correct option, and nothing else in the suite would have noticed. It is an array now, deduplicated once at the single place a response is built, and a storage round-trip assertion guards it. Caught by exercising the real app, not by the tests — which is itself the argument for walking the thing after a refactor rather than trusting green.
