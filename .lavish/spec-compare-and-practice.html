01 Removing slot from WordSpec

Yes — and it is a bigger, better change than you described. You framed it as deleting a field. What it actually does is split one overloaded type into the two things it has been standing in for, and collapse each engine from two entry points to one.

You already made this decision, halfway

When you restyled the conjugators, you changed the engine signature to conjugate(spec, slot). From that moment the engines stopped reading spec.slot — they read the argument. So today there are two sources of truth for which ṣīghah is being built, and nothing checks that they agree: 

// today — both of these are "valid" and they disagree
conjugate(wordSpec({ root, formId: 'I', tense: 'madi', slot: '3ms' }), '1p')
//                                                    ^^^^^ ignored      ^^^^ wins

The service papers over it by passing spec.slot as the argument. That is not a design; it is a seam left over from the change. Removing the field closes it.

What the type actually is

A spec with no slot is a paradigm: مدّ · Form I · muḍāriʿ · maʿlūm · marfūʿ. A slot indexes into it. Those are two different things and the codebase already says so in three places — fullTable(spec) ignores the slot, chartOf() exists purely to null it out, and slot: null is the documented way to mean "this is a chart".

The naming consequence, which I'd not skip If the object no longer names a word, it should not be called WordSpec. Call it ChartSpec (or ParadigmSpec). Then "WordSpec" is free to mean what history and the quiz layer actually store: ChartSpec + slot. Keeping the old name on the new meaning is how a codebase gets a type whose name lies — which is the exact problem ChartID had before you dismantled it.

The strongest argument: one method per engine

Every engine currently implements conjugate and conjugateTable, and nothing but a test stops them from disagreeing. I had to write a 5,220-chart consistency sweep precisely because they can — and it caught a real bug (my first muḍāʿaf table builder emitted rows in ṣīghah-block order instead of sarf order). If tables are the only thing an engine builds, that entire class of bug stops existing and the sweep can be deleted: 

// the service keeps a single-word convenience; the engines lose one method each
export function conjugate(spec, slot) {
  return fullTable(spec)?.[slot] ?? null;
}

What it costs — measured, not guessed

I ran both shapes over the whole lexicon (58 roots · 5,220 charts · 68,440 cells). Table-first is faster for anything that walks a paradigm, and the single-word penalty is real but far below anything a phone would notice:

WorkPer-cell callsTable-firstVerdict
Every cell in the lexicon (68,440 words) 6.3 ms4.4 ms table-first 30% faster
1,000 single words (worst case: makeFromMeaningQuestion retries) 0.1 ms1.2 ms 12× slower, still 1.2 ms
poolProfile(), which already walks every slot of every chart strictly fewer calls, same words wins outright

So the "throw away 13 of 14 words" objection is real in principle and irrelevant in practice. If it ever matters, a Map keyed by rootKey|form|chartKey makes the second call free — but I would not build that until something is slow.

What would have to change

  • Engines — delete conjugate, keep conjugateTable(spec). Both implemented engines already have both, so this is a deletion.
  • Service — conjugate(spec, slot) becomes the two-liner above. citation() asks for the māḍī and muḍāriʿ tables and takes ['3ms'].
  • word-spec.js → chart-spec.js — atSlot, chartOf, slotSpecsOf all go away and the factory is renamed chartSpec(); that file gets noticeably smaller. Done — Aug 2026.
  • Quiz layer — the one that pays. randomWordSpec returns { ...chartSpec, slot, word } today; it keeps doing that, but the flattened object is now honestly "a chart plus a slot" rather than a spec with a mystery field. Roughly a dozen call sites, all mechanical.
  • History — unchanged. It stores chartKey + slot already.
The one thing I'd watch fullTable() returns null for an impossible chart but an object otherwise, so fullTable(spec)?.[slot] ?? null quietly handles both. Keep that; don't "simplify" it into returning {}, or availableCharts() starts counting empty charts as real ones — that exact bug already appeared once in conjugateTable.
Drop slot from the spec and make tables the only thing engines build?
My recommendation is the second option — the rename is most of the value.

02 Two tables side by side

This is the cheapest of the three, because the refactor already paid for it. A chart is now a plain object of axes and fullTable(spec) returns {slot: word}. A comparison is therefore two specs and a diff — no engine work at all.

The framing that makes the UI fall out

Every comparison you named is the same shape: take a chart, change one or more axes, show both. The axes are exactly the spec's fields plus the root: root · form · tense · voice · mood. "Manṣūb beside majzūm" varies mood. "Form I muḍāriʿ majhūl beside Form II muḍāriʿ maʿlūm" varies form and voice. كتب beside مدّ varies the root — and for a ṣarf app that one is the most instructive of all, because it is sound against doubled.

A · Two independent pickers

Most taps

Left and right each get the full Tables picker. Maximum freedom, and you can compare two unrelated things.

But it makes the common case (change one thing) as expensive as the rare case, and nothing teaches the user that a comparison is about an axis.

B · "Vary by" chip

Fewest taps

Pick one chart, then tap an axis: voice shows maʿlūm beside majhūl, iʿrāb shows the three moods.

Beautifully fast and self-explaining — but it can only ever vary one axis, so your Form I majhūl vs Form II maʿlūm example is impossible.

C · Base + delta

Recommended

Pick a base chart. The right column starts as a copy, and you tap only what differs — one tap for the common case, two or three for a cross-comparison.

Model B rides on top of it for free: the "vary by" chips are just presets that write one field of the delta.

The part that earns it: the diff

Showing two tables next to each other is worth little; showing which letters moved is the whole feature. Three levels, and I'd build all of them because each is a few lines:

  • Row level — mark each row same or different, and dim the identical ones so the eye lands on what changed.
  • Letter level — trim the common prefix and suffix, colour the middle. Words come out of the engine NFC-normalised, so compare grapheme clusters (a letter plus its ḥaraka is one cluster) via Intl.Segmenter, not code units — otherwise you highlight half a ḍamma.
  • Table level — one summary line: "9 of 14 rows differ", or "these two charts are identical".

This feature is also a test — I found the bug again while writing this section Put ظلل Form II manṣūb beside majzūm and the app would say "identical". Form II never merges, so it must behave like a sound verb: يُعَلِّمَ vs يُعَلِّمْ differ, and يُظَلِّلَ vs يُظَلِّلْ should too. This is the MUDAAF_ENDINGS.mudari_jazm issue still outstanding — a comparison view surfaces it on sight, which is an argument for building this before the weak-verb engines land, not after.

Where it lives, and what it costs

Inside the Tables tab, as a Compare button beside "View table" — you have already chosen a chart by the time you want to compare it, so a separate tab would make you choose twice. Roughly: one state.compare delta object, one render function, one diff helper, and about 40 lines of CSS. No engine, grammar or service changes.

Two extensions worth designing for now even if built later: a third column for the wazn (فَعَلَ pattern) alongside any real verb, and a deep link from quiz feedback — "you wrote the manṣūb; here it is beside the majzūm you were asked for", which turns a wrong answer into the exact comparison that explains it.

03 Practice — the names and the flow

The current tab shows 33 controls in 7 rows, all at once, with dependencies that only reveal themselves after you interact: pick amr and the voice row greys out; drop muḍāriʿ and iʿrāb greys out; pick derived nouns and four rows vanish. Someone who knows the app reads it fine. Someone who doesn't cannot tell what a session will feel like until they start one.

Names — one rule fixes all four

Name each type by what you are given → what you must supply, phrased as something the user does. Every current name breaks that rule differently: "Identify" doesn't say identify what, "Meaning → verb" uses an arrow a beginner has to decode, and "Derived nouns" names a topic rather than an action.

Only two names change, but the subtitles are the real fix: they are the first place the app says what a question looks like. Note produce also gets a better Arabic label — كِتَابَة is "writing" the physical act, صِيَاغَة is forming/derivation, which is what the user is doing.

Flow — your wizard, and two alternatives

A · Step-by-step wizard (your idea)

Type → scope → charts → count → summary. Each step explains itself, nothing greys out because irrelevant steps are skipped entirely.

Cost: five screens to change one chip. Repeat users will feel it by session three.

B · One screen, collapsed sections

Same single screen, but each section collapses to a summary line once set — Tense · māḍī, muḍāriʿ › — and expands on tap with its explanation.

Cost: keeps the wall-of-chips feeling for a first-timer, just folded up.

C · Presets first, wizard behind "Custom"

Recommended

Practice opens on 5–6 named setups with real subtitles. "Custom…" at the bottom runs your wizard. Returning users get "Last setup" as the first card.

Why: most sessions don't need 33 controls, and a preset list is documentation.

04 What I'd do in what order

  • Fix the Forms II/V endings first. It is one line, it is wrong Arabic in 40 cells, and both other features would display it prominently.
  • Then the ChartSpec split (§01). Do it before the comparison view and before the weak engines, because both would otherwise be written against a type that is about to change.
  • Then the comparison view (§02). Cheap, immediately useful to you as the author, and it doubles as a correctness instrument for the ajwaf / nāqiṣ / mithāl engines while you write them.
  • Then Practice (§03). It is the biggest UI job and the only one with no engine risk, so it can land last without blocking anything.
